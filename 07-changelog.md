# 07 · Changelog

## 2026-10-13

- Роли «Бухгалтер» (`payment-accountant`) и «Экономист» (`payment-economist`) рядом с Payment Admin. Права ролей описаны в `server/src/lib/roles.ts`; bootstrap создаёт роли, выдаёт и отзывает права, назначает пользователей из `PAYMENT_ACCOUNTANT_*` / `PAYMENT_ECONOMIST_*`. `GET /api/admin/session` возвращает `role` и `capabilities`, админка показывает только разрешённые разделы и после входа открывает раздел роли.
- Раздел «Финансы» (админ, бухгалтер): поступления/возвраты/итог по валютам и в тенге, «Требует внимания» (несверенные оплаты, спорные, возвраты в работе), итоги по дням для сверки с выпиской, реестр оплат со сменой статуса сверки прямо в таблице, реестр возвратов, CSV для Excel.
- Раздел «Аналитика» (админ, экономист), без персональных данных: чистая выручка, средний чек, конверсия ссылок, срок до оплаты, доля возвратов, выручка по месяцам (график + таблица), резидентство, валюты, география, воронка, индивидуальные цены против стандартных, ожидаемые поступления по возрасту ссылок, текущая цена.
- Бухгалтер может менять только `accountingStatus`, `refundStatus`, `refundReason`, `adminComment`; в карточке оплаченной транзакции появился блок «Учёт и возврат».
- Дата возврата `refundedAt` теперь сохраняется в базе (раньше вычислялась, но терялась при записи).
- Статус возврата защищён от противоречий: отметить возврат можно только у оплаченного заказа, а выполненный возврат больше не меняется (раньше API принимал `refundStatus=processed` у неоплаченного заказа и сброс на `none` у уже возвращённого).
- `GET /api/admin/reports/export.csv?report=__proto__` (и другие имена из прототипа объекта) отвечал 500, теперь 400.
- Причина возврата обязательна для статусов «Запрошен», «Одобрен», «Выполнен» (API и форма).
- При лимите попыток входа (429) показывается «Слишком много попыток входа. Подождите минуту», а не общая ошибка.
- В лог пишется предупреждение, если env-списки ролей переводят пользователя из одной платёжной роли в другую.
- Пока отчёт перезагружается, статусы сверки в реестре заблокированы; пресет периода подсвечивается тот, что выбран; ошибка периода — на языке интерфейса; пустой период — «нет данных» вместо пустого графика.
- Общие хелперы клиента (API, токен, форматирование) вынесены в `client/src/shared.js`, отчёты — в `client/src/admin-reports.jsx`.

## 2026-10-06

- PDF-квитанция об оплате (`server/src/lib/receipt-pdf.ts`, ru/kk/en): реквизиты ННМЦ, плательщик, назначение, дата, маска карты, референс Halyk. Прикладывается к письму плательщику и админу после подтверждения оплаты.
- Скачивание квитанции: `GET /api/payments/:id/receipt.pdf` (только для оплаченных заказов, кнопка на странице успешной оплаты) и `GET /api/admin/orders/:id/receipt.pdf` (кнопка в истории транзакций).
- Цена задаётся в базовой валюте на выбор (KZT или USD), вторая считается по курсу.
- Курс USD/KZT: официальный курс НБ РК (`lib/exchange-rate.ts`, обновление cron'ом раз в час) или ручной. Уже отправленные ссылки сохраняют свою сумму.
- Отслеживание открытия ссылок на оплату: поля приглашения `firstOpenedAt`/`lastOpenedAt`/`openCount`, `POST /api/invitations/:id/opened` (вызывается страницей оплаты только в видимой вкладке; админские браузеры не считаются), вычисляемый статус `invitation_opened` («Ссылка открыта») и строка «Открыта N раз · впервые … · последний раз …» в истории транзакций. Хранимые статусы приглашения не меняются.
- e2e-тесты больше не берут SMTP из локального `.env`.
- Открытие ссылки пишется атомарным обновлением одной строки (`recordInvitationOpen`), а не через `updateStore`: не читает всю базу, не меняет версию приглашения и не тормозит постбэки Halyk. Общая запись хранилища поля открытий не перезаписывает.
- Открытия не засчитываются для автоматизированных браузеров (`navigator.webdriver`); история открытий видна и в карточке неоплаченного заказа.
- Сайт больше не падает целиком, когда браузер блокирует localStorage/sessionStorage (Safari «Блокировать все cookie», приватные режимы).
- Исправлены дубли заказов на Postgres: параллельные запросы на оплату одной ссылки (двойной клик, две вкладки) создавали по заказу на каждый запрос (воспроизводилось 5 из 5). Проверка версии теперь одним атомарным `UPDATE … WHERE version = ?` (`updateMany`), хранилище читает приглашения раньше заказов, создание заказа всегда обновляет версию приглашения. SQLite этим не страдал — транзакции записи там последовательны.
